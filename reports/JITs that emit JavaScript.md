# JITs emit JavaScript the host optimizes

People have compiled guest programs into JavaScript functions since Marnanel Thurman’s Gnusto Z-machine, whose checked-in engine carries a 2003–2009 copyright and caches an `eval`’d function for code that lives in static memory ([Gnusto engine](https://github.com/curiousdannii/gnusto/blob/master/gnusto-engine.js), [IFWiki](https://www.ifwiki.org/Gnusto)). Vanessa Freudenberg’s SqueakJS is the project that states the stricter goal in public notes: emit ordinary JavaScript, with temps and direct calls rather than a Smalltalk stack, so the browser’s own JIT can delete type tests and fold arithmetic. The compiler on SqueakJS `main` and on the `v2` branch still transcribes bytecodes one-to-one onto the interpreter’s stack pointer and a `switch` on `vm.pc` ([SqueakJS JIT notes](https://squeak.js.org/docs/jit.md.html), [jit.js](https://github.com/codefrau/SqueakJS/blob/main/jit.js)). The compilers that actually lower guest values into JavaScript temporaries, or delete coercions the host would otherwise emit, are Andrew Plotkin’s Quixe, the Doppio JVM trace JIT, and TurboWarp’s September 2025 Scratch compiler. On CPUs, a bare 6502 (Andrea Griffini’s js6502), a Z80 Master System and Game Gear (Guillaume Cédric Marty’s jsSMS), and several MIPS cores (Paul Holden’s n64js, Joel Middendorf’s 1964js, eNGE, soywiz’s jspspemu, and the incomplete JSX) do translate guest machine code into JavaScript functions. A complete Apple II does not, and neither does any PDP-7, PDP-8, or PDP-11 emulator examined here. Sebastian Macke’s 2014 OpenRISC-to-JavaScript dynarec ran more than ten times slower than his interpreter and was abandoned; current v86 translates x86 to WebAssembly. The generator that writes the host JIT’s limits into its own source comments is n64js.

## Freudenberg’s notes describe a compiler the repository has not shipped

Freudenberg’s JIT notes, written in March 2021 and updated through November 2023, with a June 2024 implementation note, draw a bright line between emitting JavaScript and emitting JavaScript a host JIT can work on. The current compiler “is single-pass, and simply concatenates template strings for every bytecode. No analysis is performed.” The notes then say the target is the JavaScript JIT, which “will apply its own arsenal of optimizations to the code we give it,” and that SqueakJS should “keep our own optimizations to a minimum in order to have quick compiles, but structure the generated code in a way so that the host JIT can perform its own optimizations well” ([jit.md](https://squeak.js.org/docs/jit.md.html)). The concrete example is `3 + 4`. The shipped generator pushes literals with `stack[++vm.sp] = lit[1]` and then tests `typeof a === 'number'`. The proposed form puts `3` and `4` in temps so the host can delete the test and fold the addition. That is an argument for **context-to-var mapping**: on a send, pop arguments into temp vars and call a JavaScript function directly, in place of allocating a context object for the activation.

That mapping is still a design. The June 2024 update says implementation started on the `v2` branch. The `v2` README lists the high-performance JIT as a wanted change — “direct function calls, function temps as stack, args passed directly via function parameters” — and points back at the same notes and at [issue 121](https://github.com/codefrau/SqueakJS/issues/121) ([v2 README](https://github.com/codefrau/SqueakJS/blob/v2/README.md)). A different `v2` experiment, per-instance-variable properties, is marked implemented and then called impractical as of a September 2025 update. The JIT item is the one still on the want list. The checked-in compiler header, the same in substance on `main` and on `v2`, says the translator “uses the interpreter's stack pointer (SP) and program counter (PC), actual context objects just like the interpreter, no register mapping, it does not optimize sends.” Jumps are “a loop and switch,” so a method can be re-entered at a different `vm.pc`. What `generate` actually introduces are six JavaScript locals that alias interpreter objects — `context`, `stack`, `rcvr`, `inst`, `temp`, and `lit` — and a temp load is an indexed access such as `temp[6 + (byte & 0xF)]`, dropped again if the local goes unused ([main jit.js](https://github.com/codefrau/SqueakJS/blob/main/jit.js), [v2 jit.js](https://github.com/codefrau/SqueakJS/blob/v2/jit.js)). The host can keep those aliases in machine registers. A push is still an indexed store through `vm.sp`. SqueakJS 0.5, in October 2014, is described on the project site as “a simple, fast-compiling, non-optimizing JIT compiler” ([squeak.js.org](https://squeak.js.org/)). The repository’s default branch is `main`, last pushed 19 September 2025, and it is not archived.

The monomorphic-send half of the same notes is explicitly borrowed. Vyacheslav Egorov’s JSConf EU 2014 talk, “invokedynamic.js,” measures a generic `Send(self, message)` at **6.30 ops/sec** against a direct JavaScript loop at **30,034 ops/sec**, annotated on the slide as **4767× slower**, because “`Send()` is too polymorphic & can't be optimized by V8.” One relinkable function per send site, installed by ordinary JavaScript assignment, reaches **9,267 ops/sec**. Specializing the numeric case on `typeof` reaches **22,738 ops/sec**, about 25% behind the direct loop ([Egorov’s slides](https://mrale.ph/talks/jsconfeu2014/), [JSConf EU 2014](https://2014.jsconf.eu/speakers/vyacheslav-egorov-invokedynamic-js.html)). Those figures are slide-deck measurements on a modified d8, including a V8 inlining heuristic Egorov edited. Freudenberg cites the argument; the numbers come from his harness. In the inline-cache section of the notes she writes that “the scheme outlined here is partly inspired by that talk”: a per-send-site `cachedClass` / `cachedFunc` updated by assignment, because a JavaScript function cannot be patched in the middle ([jit.md](https://squeak.js.org/docs/jit.md.html)). The shipped `jit.js` header still says the compiler “does not optimize sends” and still uses `vm.send`. The citation lives in the notes. The 2014 DLS paper is about a different, already-shipped choice: Squeak objects are ordinary JavaScript objects with direct references, instance variables live in an array because bytecodes index them, and SmallIntegers are JavaScript numbers ([Freudenberg 2014](https://freudenbergs.de/bert/publications/Freudenberg-2014-SqueakJS.pdf)). That paper describes the object memory the JIT sits on. It does not describe context-to-var compilation.

## Quixe, Doppio, and TurboWarp already lower guests into host locals

The preference in those notes is a ladder, and other language VMs already stand on every rung. The bottom rung is “turn guest instructions into a JavaScript function and cache it.” The middle rung is “let straight-line values live in JavaScript temporaries, and spill back to guest memory only at an exit.” The top rung is “prove a type or a single callee, so the host inlines and deletes checks.” SqueakJS’s notes describe the top. SqueakJS’s compiler occupies the bottom, with the six alias locals as a small step up.

Gnusto is the early bottom rung, and it is a real JIT. Opcode handlers return a string of JavaScript. `_compile()` may cover the instruction at the PC and the next few. `run()` looks up `this.m_jit[start_pc]` and, on a miss, does `eval('with (this) {dummy='+this._compile()+'}')`, stores the function when `start_pc` is in static memory, and calls it. The author’s project page says subsequent executions then “run at speeds close to that of pure JavaScript” ([gnusto-engine.js](https://github.com/curiousdannii/gnusto/blob/master/gnusto-engine.js), [batmantis.com/gnusto](http://www.batmantis.com/gnusto/)). Parchment, as Atul Varma and the Parchment archive describe it, was a browser shell around that engine, “powered by Thomas Thurman's Gnusto engine” ([Parchment archive](https://code.google.com/archive/p/parchment/), [Varma’s note](https://portfolio.toolness.org/parchment/)). Dannii Willis later split the engine out, left it unmaintained, and replaced Parchment’s default with ZVM from ifvms.js. The GitHub repository is archived. IFWiki dates the first writing to 2002; the engine file that was opened starts at the 2003 copyright and a 2005 CVS stamp, so 2002 is the wiki’s date.

Quixe is the middle rung, done carefully. In version 2.2.6, `compile_path` emits a straight-line run of Glulx opcodes as JavaScript statements and stops at a call, a return, an unconditional branch, or any address that is already a branch target, because “you can't jump into the middle of a JS function.” Inside the path the compiler keeps an offstack and an offloc of numeric literals and JavaScript temporaries (`_holdN`). Pushing delays the real stack write. A jump, call, or return unloads that offstate, and the compiler refuses to finish a path that still holds it. `make_code` used to `eval`; it now does `new Function('self', val)`, and the function runs in global scope, so VM state arrives as the explicit `self` argument. The result is stored in `pathtab` only when `self.pc < ramstart`. A function in writable memory still gets a `VMFunc` and is left out of the permanent table ([quixe.js](https://github.com/erkyrath/quixe/blob/master/src/quixe/quixe.js)). Plotkin described the JIT in public on 25 May 2015 and, on 29 May, the `func(self)` calling convention, with reported speedups of **65% in Safari, 55% in Chrome, and 10% in Firefox** from that convention change ([Javascript wonkery](https://www.blog.zarfhome.com/2015/05/javascript-wonkery)). The post is about making already-generated functions optimizable. The offstate and the `ramstart` rule are documented in the source comments. Quixe constant-folds immediates into JavaScript number literals. A general load from ROM is still a runtime `self.Mem4(addr)` call, so “ROM is immutable” governs caching, and it does not govern a general constant-folder.

ZVM shows how easy it is to stop one rung short of the README’s claim. ifvms.js disassembles Z-code to an AST and compiles with `new Function('e', '' + context)`, cached on `this.jit[pc]`. `RoutineContext.toString` still begins `var l=e.l,s=e.s,t=0`, stack operands print as `s[--e.sp]`, and locals print as `l[n]`. Reconstructing Inform `if` blocks and `while` loops into JavaScript control flow exists in `idioms.js` and is commented out of the disassembler. The README says that mapping is “currently not enabled” ([ifvms.js README](https://github.com/curiousdannii/ifvms.js/blob/master/README.md), [zvm.js](https://github.com/curiousdannii/ifvms.js/blob/master/src/zvm.js), [disassembler.js](https://github.com/curiousdannii/ifvms.js/blob/master/src/zvm/disassembler.js)). A 2013 forum post described the idiom pass as working. The source and the README are the later statement. The repository was pushed as recently as 12 July 2025.

Doppio is a shipped trace JIT on the middle rung, and the 2013 technical report should be left in 2013. That report calls DOPPIO “an untuned interpreter” ([UM-CS-2013-011](https://web.cs.umass.edu/publication/docs/2013/UM-CS-2013-011.pdf)). On current `master`, a method counts down `numBBEntries` from **200**, or from **1000 × code length** when the method is three opcodes or shorter, and only then compiles. `jitCompileFrom` walks a straight line and closes the trace at a branch or an invoke. A trace of more than one opcode builds a symbolic stack and returns `new Function("f", "t", "u", emitted)`. A one-opcode trace is cancelled. Loads emit `var sN=f.locals[i]`; the operand stack is spilled back to `f.opStack` at the boundary ([jit.ts](https://github.com/plasma-umass/doppio/blob/master/src/jit.ts), [methods.ts](https://github.com/plasma-umass/doppio/blob/master/src/methods.ts)). hrj landed trace creation on 6 May 2016; John Vilk edited it afterward ([jit.ts history](https://github.com/plasma-umass/doppio/commits/master/src/jit.ts)). The last push was 6 December 2022. The tree is stale. The authors have not, in a source opened for these notes, called it retired.

Above that, three projects show what “shaped for the host” looks like when the guest is a language. PyPy.js has two layers that are easy to conflate. Emscripten compiles the PyPy interpreter itself to JavaScript ahead of time. A separate RPython backend turns a hot trace into an asm.js module — `"use asm"`, typed-array views of the heap, `function F(frame, tladdr, label)` — and the browser side compiles that string with `new Function`. Ryan Kelly described the split on 8 August 2013: the guest JIT “triggers a JIT compilation to produce new JavaScript and feeds it up into the host interpreter” ([pypy-js proof of concept](https://www.rfk.id.au/blog/entry/pypy-js-poc-jit/), [jsbuilder.py](https://github.com/pypyjs/pypy/blob/pypyjs/rpython/jit/backend/asmjs/jsbuilder.py), [library_jit.js](https://github.com/pypyjs/pypy/blob/pypyjs/rpython/jit/backend/asmjs/library_jit.js)). The runtime artifact is **asm.js**, the validated subset. The project README says development is sleeping, and the last push was 19 March 2019 ([pypyjs README](https://github.com/pypyjs/pypyjs/blob/master/README.rst)). Moonshine, by contrast, translates a Lua prototype’s bytecode into `function(...){ while(1){switch(pc){...}}}` that still calls `setR` on a register file. The flag defaults off (`shine.jit.enabled || false`) and a function is compiled after **two** invocations. Paul Cuthbertson’s November 2014 remark that Moonshine “is not a compiler” means it does not compile Lua source to bytecode; Yueliang does that. The 2013 talk listed “JIT?” as future work. The checked-in `jit.js` is the later implementation, last pushed 28 May 2021 ([moonshine jit.js](https://github.com/gamesys/moonshine/blob/master/vm/src/jit.js), [issue 28](https://github.com/gamesys/moonshine/issues/28)).

TurboWarp is the current top rung among these systems, and it says so in documentation dated to a compiler released **20 September 2025**. Scripts become JavaScript functions, or `function*` generators when a script must yield. The new compiler tracks the kinds of values each variable may hold at each point, including through loops and conditionals, and deletes numeric coercions when that analysis says they are redundant: a summing loop that used to emit `((+sum.value || 0) + (+i.value || 0))` becomes `(sum.value + i.value)` when the script runs without screen refresh and the warp timer is off. The analysis is abandoned as soon as another script might run in the middle and store a string into a variable the loop treats as a number. The page credits Tacodiva with almost all of that compiler ([How TurboWarp runs projects](https://docs.turbowarp.org/how), [New Compiler](https://docs.turbowarp.org/new-compiler)). Shumway’s famous `Vector.forEach` story is a manual edit on this same rung, and it is a story about library code. St-Amour and Guo report that one shared `forEach` for every element type was polymorphic, so the JavaScript JIT would neither treat the element access as monomorphic nor inline the callback. Cloning the method for hot variants, such as integer vectors, made those sites monomorphic. The paper gives no speedup for that clone. It says coaching a JavaScript-targeting compiler such as Shumway is future work, and its measured speedups of about **1.02× to 1.20×** are on Octane, on hand-written benchmarks ([ECOOP 2015](https://drops.dagstuhl.de/storage/00lipics/lipics-vol037-ecoop2015/LIPIcs.ECOOP.2015.271/LIPIcs.ECOOP.2015.271.pdf)).

| --- | --- | --- | --- |
| Z-machine | Gnusto | Opcode strings, `eval`, cached in static memory | Function cache |
| Z-machine | ifvms.js / ZVM | AST printed to a function with `new Function` | Stack and locals stay in engine arrays; `if`/`while` reconstruction is disabled |
| Glulx | Quixe | Straight-line paths, `new Function('self', …)`, cached below `ramstart` | Values live in `_hold` temporaries and spill at exits |
| Smalltalk | SqueakJS | One-to-one bytecode templates, `new Function` | Notes ask for temps and per-site sends; `jit.js` keeps SP, PC, and `vm.send` |
| JVM bytecode | Doppio | Hot straight-line traces, `new Function` | Operand stack lowered inside the trace; spill at the boundary |
| RPython traces | PyPy.js | Hot traces rendered as an asm.js module | Guest JIT feeds new JavaScript to the host; the interpreter itself is Emscripten output |
| Lua bytecode | Moonshine | A `switch(pc)` function, off unless enabled | Register file remains; two invocations trip compilation |
| Scratch | TurboWarp | Functions, or generators when a script yields | September 2025 analysis deletes coercions when no other script can intervene |
| ActionScript | Shumway | A Flash runtime whose paper calls it a JavaScript-targeting compiler | The published `forEach` fix is a hand clone of one library method |

## 6502, Z80, and MIPS compile; Apple II and the PDPs do not

The same split, applied to CPUs, is sharp. “The emulator is written in JavaScript” and “the emulator compiles guest machine code into JavaScript” are different claims, and a third claim sits between them: some emulators call `new Function` once per opcode, at load time, to build their own jump table. That third pattern still fetches and dispatches every guest instruction. It is static generation of the interpreter. It is not a JIT of a guest program. jsbeeb, Matt Godbolt’s BBC Micro emulator, is that pattern. `generate6502JumpTable` builds **256** handlers from `InstructionGen` templates and `exec` still calls `funcs[opcode]` for the byte just fetched ([jsbeeb opcodes](https://github.com/mattgodbolt/jsbeeb/blob/main/src/6502.opcodes.js), [6502.js](https://github.com/mattgodbolt/jsbeeb/blob/main/src/6502.js)). jsbeeb emulates a BBC Micro.

Griffini’s js6502 is a guest JIT, and it is a bare 6502. The README says “Not an interpreter, but a JIT compiler to Javascript.” `jit()` appends JavaScript for each opcode into a string, compiles it with `eval`, and caches the function in `jitcode[ip]`. A block stops at `jmp`, `jsr`, `rts`, or `brk`, and otherwise stops after **two** instructions. Every covered byte is recorded in `jitmap`. `STA`, `STX`, `STY`, `INC`, and `DEC` call `maykill`, which drops cached functions that cover the written address. The README’s limit matches the code: self-modifying writes through other opcodes, and I/O outside absolute `LDA`/`STA`, are outside the invalidation story. `CLI`, `PHP`, `PLP`, `RTI`, `SED`, and `SEI` throw “Not implemented.” `STY` contains `m.susbtr`, a misspelling that throws when that line runs. `ADC` and `SBC` never consult the decimal flag. The tree is a CPU, a tiny assembler, and canvas demos. There is no Apple II ROM, disk, or language card. The last commit is 15 October 2023, “updated demos” ([js6502](https://github.com/6502/js6502), [6502.js](https://github.com/6502/js6502/blob/master/6502.js), [README](https://github.com/6502/js6502/blob/master/README)).

apple2js is the complete Apple II, and its CPU is an interpreter. `CPU6502.step` does `this.op = this.opary[this.readBytePC()]; this.op.fn()`, with `opary` filled from opcode maps. A search of that file found no `new Function` ([cpu6502.ts](https://github.com/whscullin/cpu6502/blob/main/js/cpu6502.ts), [apple2js package.json](https://github.com/whscullin/apple2js/blob/main/package.json)). No complete Apple II emulator in the set examined here — apple2js, its cpu6502 core, jsbeeb, and js6502 — dynamically translates guest 6502 programs into JavaScript. A private or unindexed project would not have appeared in that search.

The PDP result is the same shape. The Will Wright cabinet’s architecture note states it directly: “Cabinet does **not** currently compile PDP-7 programs into JavaScript; it interprets guest instructions and tests their behavior. SqueakJS's guest-language JIT is a useful precedent, not a feature Cabinet already has” ([ARCHITECTURE-AND-LINEAGE.md](https://github.com/SimHacker/WillWrightShowForFood/blob/main/packages/cabinet/ARCHITECTURE-AND-LINEAGE.md)). `paulnank/pdp11-js`, still committed to as of 2 March 2026, emulates a PDP-11/70 by reading and writing virtual words, trapping, and decoding operands; a search of `pdp11.js` for `new Function`, `eval(`, and a step function found no compiler ([pdp11.js](https://github.com/paulnank/pdp11-js/blob/master/pdp11.js)). Archived `js-pdp8` advances a fetch cycle and is an interpreter of a simplified PDP-8 ([js-pdp8](https://github.com/MircoT/js-pdp8)). The emulators.org PDP-7 and PDP-8 pages document `cpu.step()` as one instruction ([PDP-7](https://emulators.org/emulator/pdp7/), [PDP-8](https://emulators.org/emulator/pdp8/)). Robert O’Callahan’s 1 November 2010 demo, the page a search for “JavaScript emulator runtime code generation” finds first, defines “a really simple imaginary CPU instruction set,” builds traces as strings, and `eval`s them. It is a real existence proof for runtime code generation. The instruction set in that demo is imaginary ([O’Callahan, 2010](https://robert.ocallahan.org/2010/11/implementing-high-performance-emulator_01.html)). SIMH itself is native C. A JavaScript PDP dynarec that is not indexed under those names would have been missed. None of the machines named here has one.

Z80 and MIPS are where guest-to-JavaScript compilation has actually been carried through, with very different degrees of finish.

jsSMS parses Z80 into an Esprima-compatible AST, closes a JavaScript function at a jump target or an unconditional jump, and installs it with `new Function`. The compiler README says the internals were inspired by Shumway’s AVM2. That credit is for the shape of the compiler pipeline. Shumway itself is a Flash runtime. A static pass runs at load; at runtime the dynamic recompiler “only parses a single function,” to cut latency. It refuses the job when static analysis cannot see the next PC, when the ROM pages, or when the PC can enter RAM at or above `0xC000`, and the interpreter runs instead. The optimizer constant-folds some register definitions (`b = 0x03` replaced at later uses) and then `this.`-qualifies the registers that remain, so survivors are `this.b` and `this.c`, properties of the CPU object, aside from a short whitelist of true locals (`page`, `temp`, `location`, `val`, `value`). Rearranging blocks into JavaScript `if` and `while` is still marked TODO. The repository’s last commit is 26 February 2018 ([compiler README](https://github.com/gmarty/jsSMS/blob/master/src/compiler/README.md), [recompiler.js](https://github.com/gmarty/jsSMS/blob/master/src/compiler/recompiler.js), [optimizer.js](https://github.com/gmarty/jsSMS/blob/master/src/compiler/optimizer.js), [Mozilla Hacks, 22 October 2013](https://hacks.mozilla.org/2013/10/fast-retro-gaming-on-mobile/)).

MIPS-to-JavaScript has been done five times, and only two of those codebases were moving in 2026. Holden’s n64js, on `main` with a commit on 19 November 2026, compiles a recorded trace to `return function fragment_<pc>_<ops>() { ... }` and installs it with `new Function`. When the fragment ends in the same PC and delay-slot state it started in, and the body is short enough, that body is wrapped in a `do`/`while` that runs until the emulator’s event-queue deadline, `cyclesToFirstEvent` ([n64js README](https://github.com/hulkholden/n64js/blob/main/README.md), [r4300.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/r4300.js), [recompiler.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/recompiler.js)). Middendorf’s 1964js writes the same kind of block as a `<script>` element whose text is generated from R4300 words, and looks the function up in `fnLut`. Unknown opcodes return an empty string, so they are skipped, and `syscall` is a logged TODO that also returns `""`. The CPU file was last touched on 10 July 2018; a September 2025 commit edits only the README ([1964js README](https://github.com/schibo/1964js/blob/master/README.md), [1964.coffee](https://github.com/schibo/1964js/blob/master/coffee/1964.coffee)). eNGE (`kootstra-rene/enge-js`), with a commit on 11 November 2026, builds one strict-mode function per block with `new Function` and, on a RAM store of an instruction word, resets the entry to `lazyCompile` because compiled blocks hold direct references to their jump targets. The project’s notes describe commercial PlayStation games running. An opcode-by-opcode audit against an R3000 manual was not part of this pass ([enge-js](https://github.com/kootstra-rene/enge-js), [rec.js](https://github.com/kootstra-rene/enge-js/blob/main/code/psx/rec.js)). soywiz’s jspspemu, archived, last pushed 27 March 2021, does `new Function` as well. Its README still says loops, calls, and returns are not JITted and that it “just compiles basic blocks without any kind of control flow.” The compiler source and soywiz’s own post show generated functions that contain a `while (true) switch (label)` state machine, an inner loop for a `bgtzl`, and direct calls. The README was left behind the compiler ([jspspemu README](https://github.com/soywiz-archive/jspspemu/blob/develop/README.md), [soywiz, optimizations](https://soywiz.com/jspspemu-new-added-optimizations/)). JSX (`fay59/jsx`), last committed 20 November 2012, the week it was published, does construct `new Function` bodies with a `while`/`switch` and drops them after RAM writes. It then `panic`s on much of the ISA, including the Geometry Transformation Engine operations games need in order to draw, and the README says it gets stuck when it would need the GPU ([JSX README](https://github.com/fay59/jsx/blob/master/README.md), [recompiler.js](https://github.com/fay59/jsx/blob/master/js/core/recompiler.js)).

Two well-known “JITs in the browser” are the cases that have left JavaScript. Macke’s jor1k wiki page says the 2014 experiment, commit `5245fe71`, compiled jump-to-jump chunks as JavaScript because WebAssembly did not exist yet. “The code was more than ten times slower than without dynamic recompilation,” browsers crashed, and he “gave up for more than two years.” The 2017 attempt recompiles one whole user-mode ELF into a single module — a huge `switch`, written as asm.js and compiled with Binaryen — demonstrated on `fbdemo` only. The page is titled as breaking a billion instructions per second, and a later Hacker News comment by Macke calls that proof of concept “more than 1 billion emulated machine instructions per second.” The wiki prose itself prints the 2014 slowdown and the interpreter’s “over 100 million” asm.js figure, and it does not print a measured rate for the recompiled core. A 2019 “webassembly cpu core” is a further, different thing: hand-written C (`or1k.c`) compiled with Emscripten, exporting `Step`. Current `dynamiccpu.js` fetches a Wasm binary and calls `WebAssembly.instantiate`. The fast path that boots Linux in the classic demo remains the asm.js interpreter. The repository’s last commit is 27 July 2022 ([jor1k wiki](https://github.com/s-macke/jor1k/wiki/Breaking-the-1-billion-instructions-per-second-barrier-via-Dynamic-Recompilation-and-WebAssembly), [2014 commit](https://github.com/s-macke/jor1k/commit/5245fe71ae62ed1d2dca3b66c8ddd8f743df2360), [2019 Wasm core](https://github.com/s-macke/jor1k/commit/5075e059c0f06dadeafe7740bb5561c194dca87c), [HN comment](https://news.ycombinator.com/item?id=31270543)). v86, committed to as of 30 October 2026, states the current policy in its README: “Machine code is translated to WebAssembly modules at runtime.” JavaScript under `gen/` generates the emulator’s own Rust backends from an instruction table. It does not JIT guest x86 to JavaScript ([v86 README](https://github.com/copy/v86/blob/master/README.md), [how it works](https://github.com/copy/v86/blob/master/docs/how-it-works.md)).

## n64js writes V8’s inlining budget into the generator

“Tailored so V8 can optimize it” is a generator policy with three knobs, and they are visible in current V8 and in the compilers that have bumped into them. At V8 commit `9b54e48c7af4` on 20 November 2026, TurboFan’s small-function inlining cutoff `max_inlined_bytecode_size_small` defaults to **30** bytecode units, with a related heap-number cutoff of **75**. The ordinary caps beside it are **460** bytecode for a single inline, **920** cumulative, and **4600** absolute. Small functions are exempt from the ordinary caps up to a total of **30,000**, because inlining them removes call overhead, enables load elimination and escape analysis, and removes heap-number allocations. A function of more than **60 KB** of bytecode is outside consideration. `min_inlining_frequency` defaults to **0.15**. Separately, `DEFAULT_MAX_POLYMORPHIC_MAP_COUNT` is **4**: a property access that has seen more than four hidden classes at one site becomes megamorphic ([flag-definitions.h](https://github.com/v8/v8/blob/9b54e48c7af4/src/flags/flag-definitions.h), [feedback-vector.cc](https://github.com/v8/v8/blob/9b54e48c7af4/src/objects/feedback-vector.cc), [Fast properties](https://v8.dev/blog/fast-properties)). These are the defaults of that one revision. n64js’s comments name the inlining budget and never quote these cutoffs. SpiderMonkey, as St-Amour and Guo described it in 2015, has the same shape under other names: one fixed layout becomes a definite-slot load, several layouts become a polymorphic inline cache, an unknown type becomes a VM call, and a single observed callee may be inlined under a guard. The paper’s hotness thresholds, baseline after **10** executions and Ion after **1000**, are hotness thresholds. The extracted text does not give a 2015 numeric cap on how many shapes a SpiderMonkey inline cache holds ([ECOOP 2015](https://drops.dagstuhl.de/storage/00lipics/lipics-vol037-ecoop2015/LIPIcs.ECOOP.2015.271/LIPIcs.ECOOP.2015.271.pdf)).

n64js is the CPU compiler that treats those limits as its own structure. The comment above `genSetRegS64LoHi` says to emit direct constant-indexed typed-array stores instead of calling `setRegS64LoHi` / `setRegS32Extend`, because “those helpers exceed V8's small-function inlining threshold and quickly exhaust the fragment's inlining budget.” The replacement is a store into `c.gprS32[r * 2]`. A self-loop is wrapped only when its body is at most `kMaxSelfLoopBodyOps = 16`, “while staying within the JS JIT's inlining budget.” A forward branch may not end a trace until `kMinOpsBeforeForwardBranchStop = 9`. The hard fragment cap is `kFragmentLengthLimit = 250`. Equating 16 guest MIPS ops with V8’s 30-bytecode cutoff would invent a correspondence the comments do not state. The hot dispatcher is a separate function on purpose: `executeFragment` runs “~millions of runs per second across short traces,” and it is kept out of `CPU0.runImpl()` “so the megamorphic `fragment.func()` loop does not bloat register allocation or OSR tiering across the interpreter loop” ([recompiler.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/recompiler.js), [r4300.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/r4300.js)). That is the Shumway observation handled the other way. Shumway stopped sharing `forEach` so each clone’s call site saw one type. n64js allows one call to be megamorphic by construction — every fragment is a different function — and quarantines it. Both are responses to one function body seeing many guest types. A shared `step(op, cpu)`, or one `read(addr)` used for RAM, ROM, and device registers, builds the bug Shumway hit.

Holden had already separated a guest exit from a host deoptimization in 2012, and the distinction is the third knob. A deopt, in his account, unwinds optimized code back to the type-gathering function, “the code equivalent of a plane-to-plane skydive.” The concrete bug was `SLT` calling a helper with `(int, boolean)` while every other caller passed `(int, int)`. The boolean “instantly deoptimises” the function in V8. The fix was to pass an integer. The same post records that Chrome 23 stopped optimizing `eval`’d fragment functions (V8 issue 2315) and that switching to `new Function` restored optimization: a rotate demo went from about **50–55 ms** per frame to **16–17 ms** on that laptop. Those frame times are his 2012 measurements ([n64js blog](https://n64js.blogspot.com/2012/08/i-wrote-an-n64-emulator-in-javascript.html)). The guest interrupt is a different event. `genStepPreamble` emits `rsp.step()` and then `if (c.stuffToDo) { c.pc = …; return … }`. Trace recording itself stops when `stuffToDo` is set. `executeFragment` also refuses to enter a fragment when the next event is closer than the fragment is long, and drops to the interpreter. Quixe does the analogous thing: it unloads the offstate before any operation that needs a legal game state, sets `self.pc`, and `return`s; I/O system mode is a compile-time literal, and compilation stops if that mode is unknown. jsSMS peels literal device ports into direct calls such as `vdp.dataWrite` and refuses to compile a PC that can enter RAM. SqueakJS checks interrupts on a backward jump in the generated JavaScript — decrement a counter, and `return` if the context changed — which is a guest exit written as ordinary control flow ([quixe.js](https://github.com/erkyrath/quixe/blob/master/src/quixe/quixe.js), [SqueakJS jit.js](https://github.com/codefrau/SqueakJS/blob/main/jit.js)).

Macke’s 2014 result is the measurement of getting granularity wrong in the other direction. Modern CPUs want “very small code pieces (from jump to jump),” and feeding the JavaScript engine “ten thousands of code chunks a second (obviously as JavaScript strings) simply does not work.” The CPU “was mainly busy by doing function calls,” and asm.js was worse because those calls crossed a foreign-function interface. His 2017 change is the opposite granularity: one function for the whole executable, internal control flow as a `switch`, which he also notes JavaScript cannot patch after the fact — “You have to recompile everything” ([jor1k wiki](https://github.com/s-macke/jor1k/wiki/Breaking-the-1-billion-instructions-per-second-barrier-via-Dynamic-Recompilation-and-WebAssembly)). n64js still emits many short fragment functions and then worries about inlining inside each one. Both results can stand. They were measured on different engines, years apart, and they pick different fragment sizes. Holden’s own 2012 heuristic, a minimum of about eight instructions because one- and two-instruction fragments cost more to call than they saved, is the same worry at an earlier constant. js6502’s hard stop at two instructions is the fragment size Macke and Holden both found too small, left in a dormant 6502.

What a 6502 or PDP-7 compiler would be copying, if it followed the compilers that stayed on JavaScript, is therefore specific. Quixe’s offstate is the lowering Freudenberg’s notes ask for: the top of the data stack and the live locals sit in JavaScript temporaries, and guest memory is written back at the exit. SqueakJS’s shipped `switch` is the lowering those notes are trying to leave. n64js’s inlined typed-array store is the way to spend the 30-bytecode small-function budget on the fragment body. A shared register-write helper spends it on the helper. An interrupt, a memory-mapped I/O store, or a write that might be self-modifying code is an ordinary `return` after the guest PC is stored, or a refusal to compile the region. A boolean flowing into an integer helper is a host deoptimization. Holden measured that case and passed an integer instead, so the interrupt path stayed an ordinary `return`.

## Conclusion

The work of emitting JavaScript from a guest is old, and the work of emitting JavaScript a host JIT can fold has been done beside the project that states it most clearly. Gnusto, Quixe, ZVM, Doppio, PyPy.js, Moonshine, TurboWarp, js6502, jsSMS, and five MIPS emulators all produce JavaScript functions from guest code. Freudenberg’s notes are the manifesto for the stricter subset. The file people open to see SqueakJS do it, `jit.js`, is the single-pass template compiler those notes argue with. The practice sits in Quixe’s offstate, in Doppio’s symbolic stack, in TurboWarp’s coercion deletion, in Egorov’s per-site send functions, and in n64js’s comments about V8’s inlining budget.

The machines in the question that still have none of those shapes are the Apple II as a system and the PDP-7, PDP-8, and PDP-11. The cabinet already says so for the PDP-7, and it correctly names SqueakJS as a precedent for compiling a guest language. The measured failure modes a new generator would be walking back into are also already on record: two-instruction fragments that lose to the call, a shared helper or a shared `Send` that the host will not inline, and a guest interrupt expressed as a change of type. The fragment size that has survived on JavaScript is the medium trace, values in temporaries, an ordinary return once the guest PC is written back. Macke’s later move, and v86’s current one, is the other honest outcome of the same evidence: leave JavaScript for WebAssembly when the host language will not give you a goto, a patchable code buffer, or a cheap call between compiled chunks.
