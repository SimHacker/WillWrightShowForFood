## What it was

OpenLaszlo was an open source platform for developing user friendly web based
applications that worked identically across all popular browsers and platforms:
Windows, Mac, Linux, IE, Firefox, Safari. It was released in 2001, and it was ideal
for presenting and editing raw XML data generated by PHP and other web services. In
other words, OpenLaszlo was the velvet glove for the iron fist of PHP.

It supported a rich graphics model with scalable vectors, bitmaps, movies,
animation, transparency, fonts, audio, streaming media, reusable components, user
interface widgets, control panels, property sheets, keyboard navigation, browser
back-button navigation, and advanced WYSIWYG text and graphical editing tools.

## What shipped on it

**Laszlo Mail.** EarthLink deployed Laszlo Mail to millions of their customers: a
full webmail client with WYSIWYG editing, spelling checker, and a user interface
that adapted as you resized the window. In 2006 that was science fiction in a
browser.

**Pandora.** The Pandora music discovery service used OpenLaszlo for its player.
Pandora's CTO Tom Conrad wrote at the time: "we considered everything you can
imagine: plain old HTML, AJAX, Flex, OpenLaszlo to name just a few. In the end,
Laszlo was the clear winner on all fronts. Mature, reliable, and the perfect tool
for the job. This outcome was only remarkable in that the decision was made by some
of the most capable AJAX developers on the planet."

**Pie menus, cellular automata, and The Sims.** I ported my pie menu code to
OpenLaszlo, rewritten to take advantage of constraints, events, prototype
customization, and XML data binding, and used it in my own applications: the Sims
Content Catalog, a von Neumann 29-state cellular automata implementation, and an
experiment comparing pie menus against linear menus.

**Micropolis.** The web front end for the open source SimCity used a
TurboGears/AMF/OpenLaszlo/Flash client-server interface. The
[archived LZX source](https://github.com/SimHacker/micropolis/tree/master/laszlo/micropolis/classes)
lives in the micropolis repo, and the
[Micropolis in OpenLaszlo retrospective](https://github.com/SimHacker/MicropolisCore/blob/main/documentation/openlaszlo/README.md)
analyzes it in exquisite detail. Video:
[Micropolis Online Web Demo](https://www.youtube.com/watch?v=8snnqQSI0GE).

**SimFaux.** An interactive TV-station simulator: an OpenLaszlo/Flash parody of Fox
News built for the Huffington Post Contagious Festival (2006), with pie menus,
channel surfing, keyword-tagged characters, video bites, surveys, and games. It
exercised everything at once — media streaming, data binding, prototype
customization — as satire. The genome and the reincarnation plan live in
[apps/simfaux](../../../../apps/simfaux/README.md): the 2006 LZX tree preserved as
DNA, to be transcribed into a working
[OpenLaszlo 5.0](https://github.com/davidtemkin/openlaszlo-5.0) app and a
[Declare](https://github.com/davidtemkin/declarelang) app as sibling organelles.
Video: [SimFaux: The Me Show](https://www.youtube.com/watch?v=gRodlxUZ9SQ).

**The Laszlo Explorer.** The reference manual was itself a Laszlo application with
embedded live examples, and "Laszlo in 10 Minutes" let you edit the example code,
dynamically recompile, and instantly see the results as a running application, in
2005, in a browser.

## The LZX language

OpenLaszlo source code is written in LZX: XML with embedded JavaScript. LZX let you
extend XML by defining your own tags in XML plus JavaScript. Once you make your
peace with XML, which seemed like a prudent thing to do at the time, it is a really
productive, enjoyable way to program — but that is thanks to the design of
OpenLaszlo itself rather than to XML.

The essentials, each treated in depth elsewhere:

- **Declarative programming.** Describing what to do instead of how to do it: XML
  declares JavaScript classes, creates instances, configures them with constraints,
  and binds them to XML datasets. Everything dovetails: objects, prototypes, events,
  constraints, data binding, instance-first development.
- **Constraints.** Attribute values defined as `${...}` expressions over other
  attributes, kept up to date automatically like a spreadsheet. The mechanics, and
  the comparison with Garnet's pull system, are in
  [Constraints and Prototypes in Garnet and OpenLaszlo](constraints-garnet-openlaszlo.md).
- **Prototypes and instance-first development.** Any attribute you can attach to a
  class you can attach to an instance; a class definition looks like an instance
  definition; a class name becomes a new XML tag. This is the Instance Substitution
  Principle, covered in [Instance-First Development](instance-first-development.md).

## XML data binding

XML data bindings are XPath based constraints that create two-way connections
between object attributes and XML data. When a data bound attribute changes, the XML
data and all constraints that depend on it update, so multiple views and editors of
the same data stay synchronized automatically.

Data bindings can also cause replication of exemplary Laszlo objects: declare how
one object looks in terms of one XML element, and Laszlo automatically replicates a
separate instance for each element in the dataset. That is the prototype system and
the constraint system and the data system all conspiring together, and it is the
feature that made data-heavy interfaces like mail clients and catalogs so quick to
build.

## Architecture: server, SOLO, and multiple runtimes

The OpenLaszlo Server dynamically compiled LZX programs, libraries, and binary
resources into SWF files; acted as a proxy so the Flash player could talk to other
servers; performed XML-RPC and SOAP calls; managed persistent connections; and
transcoded media formats into things the Flash player could digest.

But applications could also run in SOLO mode — Standalone OpenLaszlo Output — talking
directly to your PHP server or any XML web service, with no Laszlo server at all,
even deployed as desktop applications.

The architecture was platform independent by design: high level LZX in, some
runtime's executable out. Flash was merely the first target. The LZPIX photo
application demonstrated the same OpenLaszlo source code identically deployed to
DHTML or Flash, and OpenLaszlo apps ran on phones via Flash Lite. This is the
important point Flex missed: OpenLaszlo abstracted the Flash player away, while
Flex existed to lock you into it.

## Why Flash, and Flash's limitations

In 2006 the Flash player was freely available, often pre-installed, deployed on 97%
of desktops, and perfectly consistent across platforms, which DHTML then was not.

But Flash had no JavaScript compiler or interpreter in the player, so the Laszlo
compiler translated source to bytecode ahead of time — no eval, no runtime class
loading without recompilation. It could only read a limited set of media formats,
so the server transcoded. It had an XML parser but no XPath or XSLT, so the
OpenLaszlo runtime supplied XPath and data binding as an alternative to XSLT. Its
security model required crossdomain.xml permission files on any server it fetched
from, so the OpenLaszlo Server or PHP acted as a proxy — and an intelligent proxy
could go further, transforming and mashing up web services on the way through.

These constraints also explain the shape of the constraint system: see
[pull versus push](constraints-garnet-openlaszlo.md#pull-versus-push).

## The interactive debugger

Open any application with `?debug=true` and you got a live Laszlo Debugger window: a
JavaScript REPL into the running application, where every object printed as a blue
hyperlink you could click to inspect its attributes, walk `parent` up to the canvas,
call `setAttribute` and watch the screen change. `Debug.write()` logged any values
as clickable object links. For 2005-era web development, being inside the living
application like that was closer to a Lisp machine or Smalltalk image than anything
else in a browser.

## Where it sits in history

The timeline matters, because credit rarely flows backwards:

- **1963** — Ivan Sutherland's Sketchpad: constraints, instances, direct manipulation.
- **1990** — Garnet at CMU: prototypes plus automatic constraints in Common Lisp.
- **2001** — OpenLaszlo released, open source, compiler-driven constraints in XML/JS.
- **2004** — Adobe Flex released, inspired by Laszlo. Flex missed the point of
  several of the most important aspects: first and foremost being cross platform
  rather than locking you into Flash (which was the entire point of Flex), but also
  the declarative constraints, Instance-First Development, and the Instance
  Substitution Principle. Flex was an expensive knock-off of Laszlo, but OpenLaszlo
  was free.
- **2006** — XULRunner's initial release, for perspective, five years after OpenLaszlo.

There is also a deeper lineage on the "rich apps over thin wire" axis: AJAX is old
NeWS. Long before the buzzword, NeWS put a programming language on each side of the
connection, implementing custom application-specific protocols with immediate local
feedback and no network round trips. OpenLaszlo was non-toxic AJAX: same
architectural idea, delivered through a compiler and a ubiquitous runtime instead of
hand-rolled DHTML hacks.

## What happened, and what survives

Flash died and OpenLaszlo went obsolete with it; the DHTML runtime never got the
investment to carry the platform alone. But I really got in the zone with it —
"Residential, Commercial and Industrial zones" — and nothing since has matched that
groove until Svelte 5's runes, which recreate the compiler-wired reactive
programming model with standard unbastardized JavaScript and HTML instead of Flash
and XML. That story, including what Svelte still misses, is in
[Svelte 5 Runes, Heir of OpenLaszlo](svelte-runes-openlaszlo-heir.md), and the piece
Svelte misses is precisely [Instance-First Development](instance-first-development.md).
