# Host JIT shaping for guest compilers

Notes for someone emitting JavaScript from a 6502 or PDP-7 compiler. Every claim below is tied to a URL and a location. Numbers from an old engine or an old experiment are labeled as such. Current V8 defaults are from one fetched revision and are not stable API.

## What V8 limits show up in real generators?

### Takeaway

Three host limits show up as generator policy. V8 inlines a callee for free only while that callee’s bytecode stays under a small-function cutoff, and a caller has a finite cumulative inlining budget. A property access stays on the fast path only while every object at that site keeps one shared hidden class (map) and fast, not dictionary, properties; after a few maps the site becomes megamorphic. n64js, in current source comments, treats both the inlining budget and a megamorphic `fragment.func()` call as things the generator must shape around. It does not quote V8’s numeric cutoffs.

### Cited Findings

- V8’s optimizing compiler can inline a property access when the hidden class proves the object layout. Hidden classes are created on the fly; objects that gain the same named properties in the same order share one hidden class via a transition tree. The first field of a JavaScript object points at its hidden class. — [Fast properties in V8](https://v8.dev/blog/fast-properties), sections “HiddenClasses” and the transition-tree example
- Named properties kept in the linear properties store are “fast” and are accessed by index after a descriptor-array lookup. If many properties are added and deleted, V8 switches the object to “slow” dictionary properties. Inline caches do not work with dictionary properties, so those accesses are slower. Integer-indexed elements are tracked separately from named properties and do not appear in the descriptor array. — [Fast properties in V8](https://v8.dev/blog/fast-properties), sections on elements versus named properties and “Fast vs. slow properties”
- A `Map` is the hidden class: the first pointer in the object, compared by identity. A `DescriptorArray` lists the properties. A `TransitionArray` answers “if this property name is added, which map comes next?” — [Maps (Hidden Classes) in V8](https://v8.dev/docs/hidden-classes), opening data-structure list
- In current V8 source (commit `9b54e48c7af4`, committer date 2026-11-20), TurboFan’s small-function inlining cutoff is `max_inlined_bytecode_size_small` default **30** (bytecode size, not source characters). A related cutoff `max_inlined_bytecode_size_small_with_heapnum_in_out` defaults to **75**. The comment says small functions ignore the ordinary caps because inlining them removes call overhead, enables load elimination and escape analysis, and removes heap-number allocations. Those ordinary caps, in the same block, are `max_inlined_bytecode_size` **460** (“maximum size of bytecode for a single inlining”), `max_inlined_bytecode_size_cumulative` **920**, and `max_inlined_bytecode_size_absolute` **4600**. The small-function exception itself is capped by `max_inlined_bytecode_size_small_total` **30000**. `min_inlining_frequency` defaults to **0.15** (“minimum frequency for inlining”). `max_optimized_bytecode_size` defaults to **60 * KB** of bytecode before TurboFan will even consider the function. — [src/flags/flag-definitions.h](https://github.com/v8/v8/blob/9b54e48c7af4/src/flags/flag-definitions.h) lines 1546–1576 and 1570–1573, fetched from `main` at that commit
- The same revision defines `DEFAULT_MAX_POLYMORPHIC_MAP_COUNT` as **4** and `max_valid_polymorphic_map_count` as that default: “maximum number of valid maps to track in POLYMORPHIC state.” Feedback code uses that flag to size polymorphic entries and, when the count is exceeded, installs a megamorphic sentinel. — [src/flags/flag-definitions.h](https://github.com/v8/v8/blob/9b54e48c7af4/src/flags/flag-definitions.h) lines 3331–3333; [src/objects/feedback-vector.cc](https://github.com/v8/v8/blob/9b54e48c7af4/src/objects/feedback-vector.cc) around the `kMaxElements = v8_flags.max_valid_polymorphic_map_count * …` check and `ConfigureMegamorphic()`
- These V8 numbers are engine defaults at one revision. They are not what n64js hard-codes. n64js’s own comment, in the code generator, is: “Emit direct constant-indexed typed-array stores instead of calling `setRegS64LoHi` / `setRegS32Extend`: those helpers exceed V8's small-function inlining threshold and quickly exhaust the fragment's inlining budget.” The replacement is a direct store into `c.gprS32[r * 2]` and `c.gprS32[r * 2 + 1]`. — [src/cpu/recompiler.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/recompiler.js) lines 702–709, `genSetRegS64LoHi`
- n64js also caps a self-looping fragment body at `kMaxSelfLoopBodyOps = 16`, with the comment that 16 guest ops covers 9–11 instruction inner loops “while staying within the JS JIT's inlining budget.” A forward branch may not end a trace until `kMinOpsBeforeForwardBranchStop = 9`, “still keeping non-loop traces small enough for JS JIT helper inlining.” The hard fragment cap remains `kFragmentLengthLimit = 250`. — [src/cpu/r4300.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/r4300.js) lines 46–62
- The hot dispatcher is deliberately a separate function. The comment says `executeFragment` runs “~millions of runs per second across short traces,” manually inlines the hot successor checks, and is “Kept in a standalone function rather than nested inside `CPU0.runImpl()` so the megamorphic `fragment.func()` loop does not bloat register allocation or OSR tiering across the interpreter loop.” — [src/cpu/r4300.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/r4300.js) lines 2977–2987
- Historical n64js heuristic, September 2012, not the current constants above: Paul Holden wrote that 1- or 2-instruction fragments cost more to call than they saved, so he required a minimum of 8 instructions, “a bit of a sweet spot,” with diminishing returns past that. The matching commit stops a trace on a branch only once `fragment.opsCompiled > 8`, or at `fragment.opsCompiled >= 250`, or when `cpu0.stuffToDo` is set. — [n64js blog, the Chrome 23 / eval post](https://n64js.blogspot.com/2012/08/i-wrote-n64-emulator-in-javascript.html), paragraph beginning “I now try to create fragments that are a minimum of 8 instructions”; [commit 855dacf](https://github.com/hulkholden/n64js/commit/855dacf3570b2d58fa00bf22e99e539035d72dea) in `r4300.js` around the old line 3762
- SpiderMonkey, as described in 2015, has the same shape story under another name. Ion turns a monomorphic, fixed-layout property access into a memory load or store (“definite slot”). If several plain-object types appear, it emits a polymorphic inline cache. If the type is unknown or exotic, it emits a VM call. A single observed callee may be inlined, with a guard; if the guard fails, execution leaves Ion code and resumes in baseline code. Footnote, labeled as of the paper’s writing: baseline compilation after **10** executions, Ion after **1000**. — [Optimization Coaching for JavaScript, ECOOP 2015](https://drops.dagstuhl.de/storage/00lipics/lipics-vol037-ecoop2015/LIPIcs.ECOOP.2015.271/LIPIcs.ECOOP.2015.271.pdf), §3.1 (footnotes 11 and 12), §3.2 “Bailouts,” §4.1 “Definite slot,” “Polymorphic inline cache,” and “VM call”

### Inferences

- A helper that is convenient in the generator (`setReg…`, a generic load, a shared `forEach`) is exactly the function that burns the small-function budget or turns a site megamorphic. n64js’s fix is to emit the store in the fragment body so the host never has to inline the helper.
- Isolating the one call that is megamorphic by construction (`fragment.func()`, a different function per trace) keeps that polymorphism out of the interpreter loop the host is trying to optimize.
- The 2012 “minimum 8 instructions” rule and the current “self-loop body ≤ 16 / forward branch ≥ 9 / absolute cap 250” rule are the generator’s own granularity knobs. They cite the host inlining budget as the reason, but they are not copies of V8’s 30-bytecode cutoff.

### Gaps

- n64js’s comments do not state a numeric V8 threshold. Equating `kMaxSelfLoopBodyOps = 16` with `max_inlined_bytecode_size_small = 30` would be an invention; one counts guest MIPS ops, the other counts V8 bytecode.
- The fetched V8 defaults are from 20 November 2026 `main`. Older Crankshaft-era cutoffs (the engine n64js was tuning in 2012) were not recovered from that tree.
- The ECOOP paper describes Ion’s PIC tactic but the extracted text does not give a 2015 numeric cap on how many shapes a SpiderMonkey PIC holds. The 10 and 1000 figures are hotness thresholds, not map counts.

## What did jor1k measure about tiny fragments versus interpretation?

### Takeaway

Sebastian Macke’s own writeup separates two experiments. In 2014, compiling each jump-to-jump chunk as its own JavaScript function was more than ten times slower than jor1k’s interpreter and fed the browser tens of thousands of source strings per second. In 2017 he stopped splitting the guest into those chunks and instead recompiled an entire user-mode ELF into one module, one big `switch`, before it ran. The page title claims a billion guest instructions per second; the prose gives the 2014 slowdown and the “over 100 million” asm.js interpreter baseline, and does not print a measured rate for the recompiled core.

### Cited Findings

- Dated on the wiki as 6 June 2017. jor1k “manages over 100 million instruction per seconds (MIPS) utilizing asm.js” and “is still based on ordinary machine code interpretation.” QEMU, by dynamic recompilation, “beats jor1k by one or two orders of magnitude.” — [Breaking the 1 billion instructions per second barrier via Dynamic Recompilation and WebAssembly](https://github.com/s-macke/jor1k/wiki/Breaking-the-1-billion-instructions-per-second-barrier-via-Dynamic-Recompilation-and-WebAssembly), opening section “Dynamic recompilation”
- “The first naive attempt (2014)” points at [commit 5245fe7](https://github.com/s-macke/jor1k/commit/5245fe71ae62ed1d2dca3b66c8ddd8f743df2360) and says it was pure JavaScript, because WebAssembly did not exist yet. His results, in his words: modern CPUs want “very small code pieces (from jump to jump),” but “to provide the JavaScript engines ten thousands of code chunks a second (obviously as JavaScript strings) simply does not work.” “The code was more than ten times slower than without dynamic recompilation.” The engine “was compiling all the time,” and “The CPU was mainly busy by doing function calls.” asm.js “was even worse, because the calls run through a Foreign Function Interface (FFI).” He then “gave up for more than two years.” — same wiki page, section “The first naive attempt (2014)”
- “The second less naive attempt (2017)”: WebAssembly is “just a little bit more efficient” and “does not really solve the major problems.” The change that does, as he states it: “Recompile the whole binary executable before it is executed.” “You compile only one module, e. g one function for an application.” The recompiler reads the ELF and “autogenerate[s] a huge switch statement.” An example is the gist [ELF executable recompiled to asm.js code](https://gist.github.com/s-macke/0d79d2ba78a022269cb7859a44174015), then compiled with Binaryen. He patches Linux `__switch_to` so the emulator sees the current PID, and a helper named `recompile` launches one chosen executable. The demonstration is only `fbdemo`: interpreted via `cpu=asm`, recompiled via `cpu=dynamic`. — same wiki page, section “The second less naive attempt (2017)” and “Demonstration”
- The page title is the billion-instruction claim. A later Hacker News comment by the same author calls that proof of concept “more than 1 billion emulated machine instructions per second” and says the count is “the machine instructions, the compiled code by the JIT is able to perform on average,” including CPU state and memory access, excluding decode, and points at snippets of the form `cycles = cyles - xxxx|0`. — [HN comment on v86, item 31270543](https://news.ycombinator.com/item?id=31270543), comment by s-macke
- Separate historical table, not the fragment experiment: the Technical details wiki records interpreter and asm.js speeds swinging from about 0.5–1 MIPS on the first Chrome boot, through Firefox 22 at 33 MIPS with a worker, Firefox 23–24 falling to 4–9 MIPS, Chrome 29 at 30–60 MIPS, and later asm.js rows such as Firefox 36 at 246 MIPS on an i7-4770 for “fbdemo V2.” He writes that “changing one line of code in the Step() function could reduce or increase the speed by a factor of 3.” — [Technical details](https://github.com/s-macke/jor1k/wiki/Technical-details), section “Overall Speed Dependence observed by Testing Different Web Browsers” and the browser table

### Inferences

- The 2014 failure is a granularity failure: basic-block-sized JavaScript functions made the host compiler the bottleneck (parse and compile tens of thousands of strings per second, then call between them). The 2017 change is the opposite granularity: one function for the whole executable, with internal control flow as a `switch`, which is the same shape as the `goto` sketch earlier on that page.
- That is a different knob from n64js. n64js still emits many short fragment functions and then worries about inlining inside each one. Macke concluded that many short functions lost to the interpreter, and only a single precompiled module was worth it. Both can be true for different engines and years; they are not one rule.

### Gaps

- The wiki body never prints a measured instructions-per-second figure for the 2017 recompiled `fbdemo`. The billion figure is the page title plus the later HN comment, not a table in the writeup. The screenshot images linked from the demonstration section were not transcribed.
- The 2014 “more than ten times slower” and “ten thousands of code chunks a second” are his retrospective measurements, not a published benchmark harness. The commit page itself was not re-read (GitHub returned 503 on the patch).
- Current jor1k `js/worker/` has no `new Function` compiler; the shipping core described on the Technical details page is still the interpreter fast path. The 2017 recompiler is the experiment on that wiki page, not the default CPU.

## How do Quixe, jsSMS, and SqueakJS turn immediates, registers, and stack slots into JavaScript locals or constants?

### Takeaway

The three compilers do not do the same lowering. Quixe keeps guest stack values and locals in JavaScript temporaries (`_holdN`) or numeric literals for as long as a straight-line path allows, and spills them back to `frame.valstack` and `frame.locals` only at a point the static analysis cannot see through. jsSMS constant-folds literal register values and literal immediates inside a function, but the registers that survive are properties of `this`, not locals; a short whitelist (`page`, `temp`, `location`, `val`, `value`) stays unbound to `this`. SqueakJS does not give each stack slot its own local. It copies the interpreter’s context, stack, receiver, instance variables, temps, and literals into a handful of JavaScript locals that alias the real arrays, and it says so.

### Cited Findings

- Quixe, “a brief lecture on the offstate”: the compiler tracks “what values are on top of the VM stack” and “what values are in all the local variables” in `offstack` and `offloc`. Those lists “can contain both numeric literals and (Javascript) temporary variables.” Pushing to the offstack “delay[s] generating the code that pushes it into the real (VM) stack.” Writing an offloc “delay[s] writing it to the real local-variable array.” Temporaries “are considered immutable as long as they remain in the offstate.” Any jump, call, or return “unload[s] the offstate” by emitting the real pushes and local writes. — [src/quixe/quixe.js](https://github.com/erkyrath/quixe/blob/master/src/quixe/quixe.js) lines 1037–1058, comment beginning “A brief lecture on the offstate”
- A quoted operand is classified by its first character: constants begin with `"0"` (a constant −1 is the literal string `"0xffffffff"`), temporary variables begin with `"_"`, and anything else is an expression that may have side effects. An `"L"` operand is either a numeric constant or a `_holdN` whose assignment `_holdN = EXPRESSION` has already been inserted. — same file, `parse_operands` comment, lines 3198–3230
- Storing an untruncated constant (operand text starting with `"0"`) goes straight to `context.offstack` or `store_offloc_value` and emits no stack write. A `_hold` can be moved the same way. Anything else allocates a new hold variable and emits `_holdN=(operand);`, or a masked form for 16-bit and 8-bit stores. A store the compiler will not keep off-state emits `self.frame.locals[addr]=(operand);`. — same file, `oputil_store`, lines 1102–1177
- At the end of a path, every used hold variable and ad-hoc variable is declared in one JavaScript statement, `var` plus the joined names, written over `context.code[0]`. The path is then turned into a function with `new Function('self', val)`. The comment says this used to be `eval()`, “which let you sneak the funcname in for debugging purposes,” and that the function runs in global scope, so the first parameter must be `self`. — same file, lines 555–578 (`make_code`) and 3985–3997 (the `var` declaration and `return make_code(...)`)
- A path “implement[s] the opcodes at that address” and “compile[s] as many opcodes as we efficiently can.” Compilation stops at the first call, return, unconditional branch, “or so on,” and also at an address that is a branch destination, because “you can't jump into the middle of a JS function.” Inside the path, “we don't maintain that state opcode by opcode.” — same file, `compile_path` comment, lines 3828–3846
- jsSMS’s compiler README says the optimizer “scans the AST for patterns and apply optimizations (inlining values, replace registers by local variables…).” — [src/compiler/README.md](https://github.com/gmarty/jsSMS/blob/master/src/compiler/README.md), section “3. Optimizer”
- The pass that actually exists, `inlineRegisters`, does not introduce locals. Its comment and example replace a later use of register `b` with the literal `0x03` after `b = 0x03`. It says it is “Limited to all registers but A and F,” because A and F would require inlining `add_a`, `adc_a`, flag helpers, and so on, and that a non-literal assignment such as `b = b - 1` “forces b to be not inlinable.” A separate pass, `evaluateBinaryExpressions`, folds `this.h = 0x0903 >> 0x08` into `this.h = 0x09`. `evaluateMemberExpressions` folds `this.f = this.SZP_TABLE[0x00]` into `this.f = 0x44`. — [src/compiler/optimizer.js](https://github.com/gmarty/jsSMS/blob/master/src/compiler/optimizer.js) lines 45–54, 100–108, and 142–167
- After optimization, `convertRegisters` turns a `Register` node into an `Identifier`, and `thisifyIdentifiers` prepends `this.` to every identifier except the whitelist `page`, `temp`, `location`, `val`, `value`, and `JSSMS.Utils.rndInt`. The generated function’s parameters are `page`, `temp`, and `location`. So the Z80 registers that remain become `this.b`, `this.c`, and the rest, which are properties of the CPU object. The folded immediates are JavaScript literals. — [src/compiler/recompiler.js](https://github.com/gmarty/jsSMS/blob/master/src/compiler/recompiler.js) lines 163–186 and 192–226
- SqueakJS’s file header: “It transcribes bytecodes 1-to-1 into equivalent JavaScript code using templates… It uses the interpreter's stack pointer (SP) and program counter (PC), actual context objects just like the interpreter, no register mapping, it does not optimize sends, etc.” Jumps are “a loop and switch,” so a method can be re-entered at a different `vm.pc`. — [jit.js](https://github.com/codefrau/SqueakJS/blob/main/jit.js) lines 60–73
- `generate` emits, and then drops if unused, six JavaScript locals that alias interpreter objects: `var context = vm.activeContext`, `var stack = context.pointers`, `var rcvr = vm.receiver`, `var inst = rcvr.pointers`, `var temp = vm.homeContext.pointers`, `var lit = vm.method.pointers`. A V3 temp load is `generatePush("temp[", 6 + (byte & 0xF), "]")`, an indexed access on that alias, not a dedicated local per slot. The whole method is `new Function("'use strict';\nreturn function " + funcName + "(vm) { … }")`. — same file, lines 236–256 and 268–270

### Inferences

- Quixe is the one of the three that really does “guest temporary or immediate becomes a JavaScript local or a constant, and the guest memory is updated only at an exit.” The first-character convention (`0` versus `_`) is how every later opcode handler can tell a constant from a local without re-decoding the operand.
- jsSMS’s README oversells the lowering. The code that ships constant-folds some register defs and then stores registers on `this`. That keeps one hidden class for the CPU object only if every generated function stores the same register names in the same order; the compiler does not say that it does this for V8’s sake.
- SqueakJS’s “locals” are pointers at the guest context, so the host can keep `stack` and `temp` in machine registers, but a push and pop are still indexed stores through `vm.sp`. That matches the header’s refusal of register mapping. A 6502 compiler that wants Quixe’s trick would keep the top of the data stack in `_hold` variables; one that follows SqueakJS would keep a single `stack` local and accept the index.

### Gaps

- Quixe’s offstate is per compiled path, not a global register allocator. There is no comment that names a maximum number of live `_hold` variables.
- No example of jsSMS’s final printed JavaScript was captured, only the AST passes that produce it. The README’s phrase “replace registers by local variables” and `inlineRegisters` disagree; the code is the authority used here.
- SqueakJS issue #121 discusses a possible later compiler that would use loops instead of the switch, and then a shift toward WebAssembly. That issue is a proposal, not the behavior of `jit.js`. — [issue 121](https://github.com/codefrau/SqueakJS/issues/121)

## How do these compilers keep guest exits separate from the host’s deoptimization?

### Takeaway

The working compilers exit by an ordinary JavaScript `return` (or by not compiling the region at all) after writing the guest PC, stack, and locals back to the interpreter’s memory. Interrupts, device events, and code that might change underfoot are that kind of exit. The host’s own deoptimization is a different event: the engine throws away optimized code because a type or hidden class changed. n64js’s 2012 notes treat a deopt as a silent mis-compile of the generated JavaScript, and treat `stuffToDo` as a guest interrupt that the fragment checks and returns on.

### Cited Findings

- n64js’s generator emits an explicit interrupt exit. `genStepPreamble` emits `rsp.step()` and then `if (c.stuffToDo) { c.pc = …; return … }`. The comment says that when accurate count updating is off, `runImpl()` enters a fragment with `c.stuffToDo === 0`, so a non-zero flag here means `rsp.step()` raised an interrupt or a break. Fused branches materialize `c.delayPC` only inside that same cold `if (c.stuffToDo)` exit. — [src/cpu/recompiler.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/recompiler.js) lines 111–124 and 273–275
- Trace recording itself stops when `c.stuffToDo` is set, or the length limit is hit, or the fragment bailed out. The comment still says “last op generated an interrupt (stuffToDo set).” `executeFragment` also refuses to enter a fragment when `eventQueue.cyclesToFirstEvent < fragment.opsCompiled`, “close to another event … drop to the interpreter.” — [src/cpu/r4300.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/r4300.js) lines 3061–3066 and 2987–2993
- Holden’s 2012 post separates that kind of exit from V8 deoptimization. He describes a deopt as unwinding optimized code back to the type-gathering function, “the code equivalent of a plane-to-plane skydive,” and says you want to avoid it. The concrete bug was `SLT` calling `setZeroExtend` with `(int, boolean)` while the rest of the program called it with `(int, int)`. The boolean “propagate[d] through to the called function, and in the case of V8, that instantly deoptimises it.” The fix was to pass an integer. He also records that Chrome 23 stopped optimizing `eval`’d fragment functions (V8 issue 2315) and that switching to `new Function` restored optimization: the rotate demo went from about 50–55 ms per frame to 16–17 ms on that laptop. Those frame times are his 2012 measurements on Chrome 21/23. — [n64js blog](https://n64js.blogspot.com/2012/08/i-wrote-n64-emulator-in-javascript.html), the deoptimization section beginning “All values are represented as 32-bit integers” through the `SLT` fix, and the earlier `eval` / `new Function` section
- Self-modifying or not-yet-fetched code is a guest exit, not a deopt. Commit 2bd45eb (26 September 2012) says a TLB miss that returned a dummy NOP was being compiled into a fragment, “so after enough iterations, the real op was magically compiled out of the running code.” — [commit 2bd45eb](https://github.com/hulkholden/n64js/commit/2bd45eb96065ce1c3922dd127b70127231b5ea03)
- Quixe unloads the offstate before any operation that “requires a legal game state,” and the compiler refuses to finish a path with a non-empty offstack or offloc (`fatal_error` if it does). The path then sets `self.pc` and `return`s. A function that “is not in ROM” still gets a `VMFunc`, “but we will not add it to the permanent vmfunc_table.” I/O system mode is a compile-time literal; “if it becomes unknown-at-compile-time, we stop compiling.” — [quixe.js](https://github.com/erkyrath/quixe/blob/master/src/quixe/quixe.js) lines 581–589, 1224–1227, 3862–3864, 3971–3975, and 3980–3983
- jsSMS will not turn a ROM into JavaScript at all when static analysis cannot see the next instruction, when the ROM uses paging, or when the Z80 PC can enter RAM at or above `0xC000` (“very similar to an `eval()`”). “When it is not possible to recompile JavaScript at all, the interpreter is used.” The dynamic recompiler parses only until a jump, “to reduce latency.” Device ports are not left as a generic call: `portPeephole` rewrites `port.out` / `port.in_` of a literal port into a direct call such as `vdp.dataWrite`, `vdp.controlWrite`, or `psg.write`, and the comment says this pass is SMS/Game Gear specific. — [README.md](https://github.com/gmarty/jsSMS/blob/master/src/compiler/README.md), “Interpreter or recompiler?” and “Dynamic Recompiler”; [optimizer.js](https://github.com/gmarty/jsSMS/blob/master/src/compiler/optimizer.js) lines 282–336
- SqueakJS checks interrupts only on a backward jump, in generated JavaScript, not by trapping a host deopt: `vm.pc = destination` and then `if (vm.interruptCheckCounter-- <= 0) { vm.checkForInterrupts(); if (context !== vm.activeContext || vm.breakOutOfInterpreter !== false) return; }` followed by `continue`. A send does the same context check and `return`s to the main loop unless the send was a primitive that did not switch contexts. The `switch` default is `vm.interpretOne(true); return;`. The header says the compiler is also invoked from `checkForInterrupts` for a long-running uncompiled loop. — [jit.js](https://github.com/codefrau/SqueakJS/blob/main/jit.js) lines 41–53, 793–805, and 997–1005
- Ion’s bailout, the host mechanism these guest exits are not, is an optimistic guard: “if a single callee is observed at a call site, Ion may optimistically inline that callee,” and if the binding changes, “execution aborts from Ion-generated code and resumes in the non-optimized … code generated by the baseline JIT compiler.” — [ECOOP 2015 paper](https://drops.dagstuhl.de/storage/00lipics/lipics-vol037-ecoop2015/LIPIcs.ECOOP.2015.271/LIPIcs.ECOOP.2015.271.pdf), §3.2 “Bailouts”
- jor1k’s 2017 writeup lists the host missing the guest operations a recompiler needs: no real goto (emulated with `switch` and `continue`), no natural “temporary halt within functions and start from there,” and no patch of an already compiled module (“You have to recompile everything”). Those are guest-exit problems. He also notes that calls between compiled modules “can be very slow” because they cross a foreign-function interface. — [jor1k wiki, 6 June 2017](https://github.com/s-macke/jor1k/wiki/Breaking-the-1-billion-instructions-per-second-barrier-via-Dynamic-Recompilation-and-WebAssembly), checklist items 3, 4, 5, and 7

### Inferences

- A guest interrupt check that is written as a normal `if` and `return`, after the guest PC has been stored, survives a host deopt and also does not cause one. A guest interrupt check that is expressed as a thrown exception, a changed hidden class, or a boolean where the rest of the fragment uses an int, becomes a host deopt and is the failure Holden measured.
- Self-modifying code and device dispatch are kept out of optimized code by refusing to compile them (Quixe RAM functions not cached, jsSMS RAM PC and paging, n64js dropping to the interpreter near an event) or by ending the compiled region before them. Invalidation, when they do get compiled, is the guest’s job: throw away the fragment and interpret. That is independent of V8 discarding an optimized function because a type changed.
- For a 6502, the same split is: memory-mapped I/O stores and IRQ polling are `return` points with the guest PC written back; an unexpected extra property on the CPU object, or a boolean flag flowing into an integer helper, is the host deopt and should not be used as the IRQ mechanism.

### Gaps

- SqueakJS `jit.js` as read does not show the image-side hook that clears `method.compiled` when a method is recompiled or a `become` happens. The header describes activation and interrupt checks, not that invalidation path.
- Quixe’s “not in ROM ⇒ not in the permanent table” is the caching rule that was found. A line-by-line write barrier that deletes an existing path was not quoted.
- n64js’s current `invalidate()` call sites were seen in `executeFragment` but the invalidation routine’s comment was not extracted.

## What does Shumway’s cloned Vector.forEach change demonstrate?

### Takeaway

One shared JavaScript function for every guest instantiation of a polymorphic type makes the element access and the callback call inside that function polymorphic, so the host will not inline them. Cloning the function per guest type gives each clone its own monomorphic call site and element access. The compiler could not make that tradeoff because it did not know which instantiations were worth the code size. The paper reports the diagnosis, not a speedup number.

### Cited Findings

- “The Shumway project, an open-source implementation of Adobe Flash in JavaScript, provides an implementation of ActionScript’s parametrically polymorphic Vector API, which includes a forEach method. This method takes a unary kernel function f as its argument and calls it once for each element in the vector, passing that element as the argument to f. Initially, the Shumway implementors wrote a single implementation of the forEach method and used it for all typed variants of Vector.” — [ECOOP 2015, §2.1 “A Tale from the Trenches”](https://drops.dagstuhl.de/storage/00lipics/lipics-vol037-ecoop2015/LIPIcs.ECOOP.2015.271/LIPIcs.ECOOP.2015.271.pdf)
- “This initial implementation performed poorly. … If the compiler observes code to be polymorphic, it may not apply crucial optimizations. For instance, the compiler may be unable to determine a monomorphic context for the element accesses and the calling of the kernel function, prohibiting optimizations such as inlining.” The engineers “determined that performance could be recouped by cloning forEach’s implementation for variants that needed high performance (e.g., vectors of integers), as the JIT would then observe monomorphic accesses and call sites.” “While the compiler lacked the necessary context to make the appropriate tradeoff decision, the Shumway engineers were able to, once they understood the optimization decisions.” — same section
- The same paper’s Ion background is the mechanism behind that failure: a definite-slot load requires one constructor and one fixed layout; several types fall through to a PIC; an unknown type falls through to a VM call. Inlining of a callee is similarly predicated on a single observed target. — same paper, §3.2 and §4.1
- n64js’s megamorphic `fragment.func()` comment is the call-site version of the same observation, handled the other way: one shared dispatcher is allowed to be megamorphic, and it is kept out of the function the host should optimize. Shumway’s fix was to stop sharing. Both are responses to one function body seeing many guest types. — [r4300.js](https://github.com/hulkholden/n64js/blob/main/src/cpu/r4300.js) lines 2983–2986; ECOOP §2.1 as above

### Inferences

- A 6502 or PDP-7 compiler that emits one JavaScript `step(op, cpu)` for every opcode, or one `read(addr)` used for RAM, ROM, and device registers, builds the Shumway bug: the single function’s load and call sites see every guest type. Cloning per class of access (zero-page versus absolute versus a specific device), or inlining the body at the site the way n64js inlines register stores, is what makes the host observe one type.
- Sharing is still right for cold paths. Shumway cloned “variants that needed high performance,” not every method. The paper’s point is that the host will not do that split on its own.

### Gaps

- The Shumway commit or file that actually clones `Vector.forEach` was not found in this pass. The ECOOP 2015 account is the primary description used here. No speedup percentage is stated in §2.1.
- The paper does not say which engine’s inliner failed on the shared `forEach`. It says “JavaScript engines” and then builds the coach on SpiderMonkey. Treating the anecdote as a V8-only measurement would go beyond the text.
